# Agentic workflow best practices

**Access date:** 2026-08-12. **Scope:** current first-party OpenAI/Codex, Anthropic Claude Code, and MCP sources. This is operating guidance, not a claim that every control exists in every product.

## Executive recommendation

Use a **small, capability-bounded roster**: one accountable coordinator, then only independent specialists (for example explore, implement, test, review). Give each a single output contract, the minimum tools and repository scope, and an isolated worktree for concurrent writes. Keep routine edits autonomous inside that boundary; require human approval for external side effects, privileged access, destructive operations, publishing, or widened network/data scope. Review the diff and validation evidence before integration.

Do not make a large permanent “agent org chart.” Both vendors make specialization, isolation, and parallel work useful, but neither documents an optimal universal roster size. Claude Code’s default *simultaneous subagent* cap is 20, which is a safety/throughput guardrail—not a recommendation to run 20 agents. Start with 2–5 active roles and increase only when representative evals show a gain. [Claude Code subagents](https://code.claude.com/docs/en/sub-agents)

[Claude](https://code.claude.com/docs/en/sub-agents) · [OpenAI](https://developers.openai.com/api/docs/guides/latest-model) |

A skill may dispatch an agent but should not be the authority for access. | Claude skills load descriptions lazily and full content on invocation; its subagents own tool/model/permission configuration. OpenAI packages skills separately from apps/actions. | Tools | Expose only task-relevant tools. Use concise, precise names/descriptions; separate read/search from mutation and explain side effects and inputs. [OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model) · [OpenAI plugins](https://help.openai.com/en/articles/20001256-plugins-in-codex/) |
| Context and persistence | Use short, stable project instructions and task briefs. Keep noisy exploration, logs, and broad search in workers. Persist only durable, reviewed facts; pass summaries rather than raw transcripts. | Claude non-fork subagents start with isolated context; OpenAI GPT-5.6 can preserve relevant reasoning across turns. [Claude](https://code.claude.com/docs/en/sub-agents) · [OpenAI](https://developers.openai.com/api/docs/guides/latest-model) |
| Loops | Bound each loop with a goal, stopping condition, turn/time/cost limit, and an evidence-producing check. Use deterministic programs for repetitive tool-heavy steps; use a model loop when a new judgement is required. | OpenAI recommends Programmatic Tool Calling for bounded, tool-heavy workflows that do not need fresh model judgement. ## Safety and autonomy policy

1. **Instructions are not authorization.** Enforce access with sandbox, filesystem/network boundary, per-tool allow/deny rules, app/source-system RBAC, and scoped credentials. Claude says permission rules are enforced by the product, not by the model; OpenAI says app approval does not override source-system permissions. [Claude permissions](https://code.claude.com/docs/en/permissions) · [OpenAI plugins](https://help.openai.com/en/articles/20001256-plugins-in-codex/)
2. **Use progressive autonomy.** Auto-approve low-risk work only within the repo/worktree and approved tool set. Ask for approval for writing outside scope, network access, credentials, data export, destructive commands, deployment/publishing, payments, or communicating externally. Approval must complement—not replace—the technical sandbox. [OpenAI safety](https://openai.com/index/running-codex-safely/) · [Claude security](https://code.claude.com/docs/en/security)
3. **Treat fetched text, tool output, repos, issues, docs, and MCP resources as untrusted data.** Do not follow instructions found there that change authority, expose secrets, or widen scope. Disable network by default where possible; do not put secrets in prompts, skill text, logs, or tool descriptions. Claude specifically requires approval for network fetch commands by default; OpenAI identifies disabled network access as a prompt-injection mitigation. [Claude security](https://code.claude.com/docs/en/security) · [OpenAI Codex safety](https://openai.com/index/introducing-upgrades-to-codex/)
4. **Hook carefully.** Hooks are executable policy/automation, not documentation: version them, restrict inputs and environment, fail closed for unsafe operations, and review them like production code. Claude hooks can block pre-tool actions, add context, run formatters, and issue notifications. [Claude hooks](https://code.claude.com/docs/en/hooks-guide)
5. **Scope MCP twice.** Declare only approved servers and tools, use user-consented roots or explicit resource/tool parameters, validate paths, and expect protocol change. The 2026-07-28 MCP release candidate deprecates Roots/Sampling/Logging in favour of parameters/resources/direct provider integration/OpenTelemetry (existing features remain compatible for at least a year). [MCP Roots](https://modelcontextprotocol.io/specification/2025-03-26/client/roots) · [MCP release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)

## Vendor-specific controls and tensions

| Topic | OpenAI / Codex / GPT-5.6 | Anthropic Claude Code (Sonnet, Opus, Fable) | Operational conclusion |
| --- | --- | --- | --- |
| Parallelism | GPT-5.6 multi-agent (beta) coordinates parallel subagents and synthesizes results; Codex app supports parallel agents and isolated worktrees. | Subagents have separate context/tool/permission boundaries; default concurrent subagent cap is 20 and nesting is configurable. | Do not translate a platform cap into a target roster. Bound ownership and merge/integration instead. |
| Model/effort routing | `gpt-5.6-sol` = frontier, `terra` = balance, `luna` = high-volume efficiency; efforts range `none` through `max`. Start at medium/baseline and compare lower effort on tasks. | Custom agents can use `sonnet`, `opus`, `haiku`, or `fable`; subagents also have effort `low` through `max` where supported. Claude documents [Fable 5](https://www.anthropic.com/claude/fable) for its hardest long-running coding/knowledge work. | Route cheap/read-only exploration to a lower-cost model/effort; reserve highest capability/effort for ambiguity, integration, security, or difficult verification. Measure the routing; high-capability models do not relax permission or review gates. |
| Context/persistence | Persisted reasoning has `reasoning.context`; GPT-5.6 defaults to `all_turns`, but it should be selected based on continuing relevance. | Subagents begin fresh unless forked; `memory: user|project|local` enables cross-session learning. | Persistence improves continuity but raises staleness and secret-retention risk. Write reviewed facts only, with source/date/owner. |
| Approval and isolation | Sandbox defines paths/network; approval defines when to ask outside it. Codex logs support audit/triage. | Read-only by default; permission modes, allow/deny rules, worktree isolation, and hooks constrain actions. | Use automatic permission modes only behind a narrow technical boundary and a human integration gate. |
| Skills/integrations | Plugin is a container for skills plus optional apps/templates; apps retain RBAC, action, confirmation, source, and domain controls. | `SKILL.md` provides instructions/resources; skills can run in forked context or preload into a subagent. | Keep workflow knowledge portable; keep credentials and mutation authority in the integration/policy layer. |

The tools and platforms therefore agree on the safety primitives, but differ in surface: Codex emphasises sandbox-plus-approval and app governance/telemetry; Claude Code exposes more per-subagent frontmatter and lifecycle-hook controls. MCP standardizes interoperability but is not itself an authorization system. Treat all three as complementary layers, never as a substitute for repository, cloud, or source-system permissions.

## Minimal rollout checklist

- Define the coordinator, up to four specialist roles, explicit file/API ownership, and integration reviewer.
- Write a skill only for a repeated, stable workflow; keep its description discoverable and its full instructions concise.
- Assign each agent an allowlisted tool set, model/effort default, max turns, and a worktree if it can write concurrently.
- Require evidence: changed paths, commands/tests, result, known failures, and residual risk.
- Run baseline evals before/after a skill, model, prompt, permission, or tool-set change; use fresh sessions.
- Turn on audit telemetry appropriate to policy; redact/minimize prompt and tool-output capture and retain it under a documented policy.
- Review hooks, MCP manifests, connectors, and credentials as code/configuration; start each external integration read-only.

## Direct implications for agent-kit

- Keep `agent-templates/` as the source of truth. Define only the small reusable roster there, with explicit ownership and stop conditions; compile its platform-specific outputs rather than hand-editing generated agents.
- Keep `skills/` workflow-only: concise trigger descriptions, scoped instructions, and test/validation recipes. Do not encode credentials, broad permissions, or unattended external mutation in a skill.
- Make the existing hook configuration the technical gate: preserve pre-tool checks for destructive/out-of-scope actions, add auditable allow/deny decisions, and treat hook edits as security-sensitive code. Do not use hooks to silently bypass human approval.
- Keep MCP config declarative and least-privilege: allowlist server/tool scope, prefer read-only tools, limit roots/resources, and keep tokens outside tracked configuration. Revalidate it as MCP evolves.
- Add a small regression suite for each shared agent/skill: trigger prompts, successful task prompts, injected/untrusted-content prompts, expected approval prompts, and a fresh-session baseline. Record quality, tool failures, approvals, cost, and latency before changing routing or autonomy defaults.
